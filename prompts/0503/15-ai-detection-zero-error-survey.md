# 15 — AI 检测 0 误报路线图 + 可解释性需求表

> **填写时长**: 约 30–45 分钟
> **重要程度**: ⭐⭐⭐⭐⭐ 用户已 7 次反馈"AI 编程窗口感测无效，运行中显示空闲，误报/瞎报/错报"——本表是终结这条隐疾的最后一战
> **依赖**: 完成 V1-§07 + V2-§13 + V2-§14
> **核心命题**: 让"AI 任务感测"从黑盒猜测升级为**可解释、可校准、可追溯**的白盒系统

---

## 引言：根因分析

**Agent B 源码扫描真相**（2026-05-03）:
- AITaskTracker 仅采用启发式 4 阶段检测（COMPILE / COMPLETION / ERROR / PROMPT 模式匹配）
- 进度估算是 8 个离散值的硬编码映射（idle=0% / thinking=30% / coding=68% / compiling=78% / validating=92% / waiting-input=98% / completed=100%）
- **完全没有真实 stdout 读取**
- **完全没有 Skill / Watchdog / SHIM**
- monitorState（细粒度）vs taskState（粗粒度）双状态可能不一致

**用户最新反馈的精确分类**:
1. **误报**: 没在跑却报"在跑"（false positive）
2. **瞎报**: 报错对象（state 字段错配）
3. **错报**: 报错方向（idle vs running 弄反）
4. **迟报**: 任务已完成才报完成
5. **漏报**: 任务变化但 DevHub 没报
6. **错后再报**: 已经误报过，过一会还重复报

**根因**：
- 启发式无 ground truth → 无 feedback loop
- 状态机双源 → UI 与业务层撕裂
- 信号黑盒 → 用户不知道为什么 detected
- 阈值固定 → 无法校准
- 无 stdout 真实信号 → 仅靠"猜"

**本表为 R8.C 的 spec-01-cli-output-parser / spec-02-shim-codex / spec-27-ai-signal-fusion-tuning / spec-28-ai-state-machine-3layer / spec-29-feedback-loop-misreport / spec-32-observability-panel 提供精确输入**。

## A. 4 状态精细区分（错误源头）

### [Q-15.A.1] 真实业务状态的精细划分  锚定 [Must]

**背景**: 当前只有 idle/thinking/running/completed 4 大态，但用户语义上有更细的分别。

**期望状态机**（请用户校准）:

| 大态 | 细态 | 含义 | 关键信号 |
|------|------|------|---------|
| **未启动** | not-launched | 工具进程不存在 | process scan = 不存在 |
| **已启动空闲** | launched-idle | 进程在但无任务 | CPU < 1% / stdout 静默 / 窗口标题"等待输入" |
| **接收输入中** | receiving-input | 用户正在打字 | 窗口活跃 + 键盘事件 |
| **思考中** | thinking | LLM 在生成 | CPU 中 / 网络上行 / stdout 含"Thinking..." |
| **真实运行** | running | 工具在执行任务（tool use / shell / 编辑文件）| 子进程派生 / 文件改动 / stdout 含 "Running..." |
| **等待人工** | awaiting-human | 任务暂停等用户决策 | stdout 含 prompt / 窗口标题"等待批准" |
| **完成** | completed | 任务结束 | stdout 含完成关键词 / 进程退出 / 窗口标题"已完成" |
| **错误** | error | 任务失败 | stdout 含错误 / 进程异常退出 |
| **卡死** | stuck | 长时间无心跳 | stdout 静默 ≥ N 分钟 + CPU < 1% |
| **未知** | unknown | 信号矛盾 | 多信号互相否定 |
