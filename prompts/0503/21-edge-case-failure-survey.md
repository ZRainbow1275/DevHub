# 21 — 边缘 case 与异常环境失败模型表

> **填写时长**: 约 35–45 分钟
> **重要程度**: ⭐⭐⭐⭐ 用户长期 24/7 跑超长 AI 任务，**异常环境的兜底**直接决定系统可用性
> **依赖**: 完成 V1-§09（cross-cutting） + V2-§13 / §15 / §17（Watchdog）
> **核心命题**: DevHub 不能仅在"理想环境"工作。本表把"网络断 / 磁盘满 / 进程爆 / 编码异常 / 时间倒退 / DPI 突变 / 多用户切换 / 反病毒拦截"等 14 类边缘环境逐一定义降级行为，避免黑盒挂死

---

## 引言：为什么必须填这份

DevHub 主用户场景是"24/7 跑超长 AI 任务批次"，意味着：

- **运行时长极长**（任务可能跑 24 小时以上），任意时刻可能撞上系统级异常
- **环境异质**（家里机 / 公司机 / 远程桌面 / VPN / 域账号），同一份代码要在 N 套环境中可用
- **不是黑盒**：异常发生时用户必须知道"DevHub 怎么处理的"，而不是"DevHub 自己挂了"

**Agent A 市场调研建议**: 借鉴 PM2 / supervisord / systemd 的"resilience patterns"——崩溃自动重启、资源配额、隔离子进程组、ETW 监听 OS 事件。

**Agent B 源码事实**: 当前 DevHub 多数 IPC 调用未做异常环境兜底，例如：
- `windowHandlers.ts` 行 463 WINDOW_SEND_KEYS 在窗口被反病毒拦截时无降级
- `SystemProcessScanner` 用 PowerShell + WMI（V1-Q-10.A.1 选 F），但**未处理 PowerShell 不可用 / 域账号策略限制**
- 主题切换无 OS 高对比度模式覆盖逻辑

**本表把 DevHub 在 14 大类异常下的行为逐一定义，作为 R8 / R8.D 的"防御性 spec"输入**。
