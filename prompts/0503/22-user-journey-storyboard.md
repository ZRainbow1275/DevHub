# 22 — 用户旅程剧本表（新用户 5 分钟 / 老用户 8 小时 / 24h 长任务 / 多机协作 / 误报恢复 / 崩溃恢复 / 首写 CSV）

> **填写时长**: 约 30–40 分钟
> **重要程度**: ⭐⭐⭐⭐ 把"功能清单"翻译为"时间轴上的体验"，让 PRD 写出来不是一堆零件，而是一段段连贯故事
> **依赖**: 完成 V1 全部 + V2-§13 / §15 / §16
> **核心命题**: 每条主用户旅程必须配齐"时间轴 / 期望画面 / 期望操作 / 关键决策点 / 失败兜底 / 5 条人话验收剧本"

---

## 引言：为什么从功能清单升级到用户旅程

R7 / R8.A / R8.B 已写 30+ spec，但用户测试后说"不顺、找不到、跑了一半就乱了"。**原因**：spec 只描述"组件能做什么"，没描述"用户从打开 DevHub 到完成目标的完整体验"。

本表把 R8 必须落地的 7 条主旅程逐一展开为剧本。每条剧本含：

- **时间轴**（按分钟 / 小时排序）
- **期望看到的画面**（What you see）
- **期望执行的操作**（What you do）
- **关键决策点**（Decision points）
- **失败兜底**（Fallback）
- **"用户能说的人话"5 条验收剧本**（关联 V2-§13-Q.G.1 用户必填 5 条）

填完后，每条剧本变成下一轮 spec 的"灵魂上下文"，PRD 不再是冷冰冰的字段清单。

## E. 旅程 5：误报后的恢复（用户标"是误报" → 系统校准 → 下次表现）

### 推荐时间轴

| 时刻  | 用户行为  | DevHub 行为  | 验收点  |
| ---------- | ---------------------------------------- | ----------------------------------------- | -------------------- |
| T+0  | 用户看到任务"running"但实际已挂  | —  | 误报暴露  |
| T+1s  | 用户点"是误报"按钮  | 弹分类（false-positive / wrong-state / late）| 用户分类  |
| T+5s  | 用户选"false-positive，CPU 信号过敏"  | DevHub 弹"信号 X 权重将从 0.20 降到 0.10"  | 透明化  |
| T+10s  | 用户确认  | 应用 + 入校准库 + 记录  | 持久化  |
| T+1min  | 用户重启该任务  | 同样情况下不再误报  | 立即生效  |
| T+1day  | 用户看到周报"过去 7 天误报率从 X% 降到 Y%" | 自动校准曲线展示  | 可量化  |
| T+1week  | 用户看到"系统建议你再标 5 个真任务以提升精度" | 主动校准提示  | 持续改善  |
