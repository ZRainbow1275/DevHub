# 23 — 可扩展性与插件体系需求表（用户脚本 / 主题 / 信号源 / SKILL / Webhook / MCP）

> **填写时长**: 约 30–40 分钟
> **重要程度**: ⭐⭐⭐⭐ 用户原话隐含"DevHub 是一个长期使用的桌面伴侣"，必须为未来 2-3 年的扩展留下接口
> **依赖**: 完成 V1-§07 / §10 + V2-§13 / §15 / §16
> **核心命题**: 在不引入云端、不破坏现有架构、不引入第三方运行时（除 Python / Node 用户已装）的前提下，为 DevHub 留出 7 类扩展接口；同时严格控制安全模型与版本兼容

---

## 引言：扩展性原则与约束

**用户既有立场**:
- V1-Q.J.3 用户要求"绝不连云端" → 插件市场仅本地，远程注册表延后
- V1-Q-7.A.1 用户已选 D（信号源插件 SDK 必须有）
- V1-Q-7.K.4 用户已选"后期"（插件市场延后到 R9+）
- V1-Q-7.G 用户已选 SKILL 公开市场作为长期方向

**Agent A 市场调研建议**:
- VSCode 扩展模型 = JavaScript + manifest + 沙箱
- Raycast 用户脚本 = TypeScript + 静态注册
- IFTTT/Zapier 风格的 Webhook 集成（不连云）
- MCP（Model Context Protocol） = Anthropic 官方协议，标准 client/server

**Agent B 源码事实**: 当前 DevHub 完全没有插件体系，所有 SKILL / 信号源 / 主题都硬编码。本表是为 R8.D 或 R9 的"开口子"提供精确蓝图。

**约束**:
1. 不破坏现有 IPC 边界
2. 不引入新进程模型（仅 worker_threads / utility process）
3. 安全优先（默认沙箱 / 显式权限授予）
4. 版本兼容（DevHub 升级不能默默作废用户插件）
